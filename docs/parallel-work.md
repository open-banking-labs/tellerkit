# 并行工作协议

> 起因：P2 收尾时并行三路子 agent，集成阶段改了三次签名不匹配
> （`AppState::new` 少参数、`audit` 作用域、`submit_transaction` 借用冲突）。
> 根因不是 agent 写得差，是**接口靠文字传递**、**冲突靠事后发现**。

## 上限在哪

并行度不由 agent 数量决定，由**接口固化程度**决定：

- 接口写在提示词里 → 每次都要人读、人比对、人修 → 并行越多，集成越慢
- 接口写成能编译的代码 → 编译器替人比对 → 并行才真正省时间

## 两条规则

### 规则一：seam 先行

分派前，集成者先提交 **seam**：新模块的类型、函数签名、文档注释，
函数体一律 `unimplemented!()`。

```rust
/// 冲正：把异常交易标记为待处置，并要求授权。
pub fn request(&mut self, req: ReversalRequest, authorizer: &dyn Authorizer)
    -> Result<ReversalRecord, ReversalError> {
    unimplemented!()
}
```

seam 提交后再分派。此时：

- agent 拿到的是**能编译的签名**，不是散文
- 它填实现，签名不对会**编译失败**，不需要我发现
- 我集成时只需合并文件，不需要对齐签名

### 规则二：枢纽文件不并行

`commands.rs`、`lib.rs`、`App.vue`、`api.ts`、`contracts/`、`package.json`、
`Cargo.toml`、`generated/` 是枢纽文件——多处依赖，改动必然交叉。

**它们只能由集成者串行改。** 如果两个任务都需要改 `commands.rs`，
它们不是两个并行任务，是一个任务的两个步骤。

## 分派前检查

```bash
node tools/plan-parallel.mjs --tasks <tasks.md> --ids T-01,T-02
```

它用仓库现有文件把 glob 具体化，报出：

- 被多个任务同时主张的文件（会打架）
- 被派去改枢纽文件的任务（不该并行）

退出码 0 才允许分派。

## 集成者的职责（不可外包）

| 职责 | 为什么不能给 agent |
|---|---|
| 契约与 seam | 需要全局视角，且决定别人怎么干 |
| 枢纽文件 | 多处依赖，改错影响所有分支 |
| 冲突裁决 | 两个合理方案相撞时，需要一个说了算的人 |
| 合并与验收 | 最终结论只能来自 `npm run gate` + 人 |

## 判据

一个批次"可并行"的标准不是"文件不重叠"，而是：

> 每个任务的实现能否在**不看其他人代码**的情况下写完并通过自己的验收命令。

做不到这一点的任务，强行并行只会把矛盾推到集成阶段——那里解决矛盾的成本更高。
