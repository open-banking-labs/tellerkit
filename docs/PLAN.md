## 0. 一页速览

| 维度 | 结论 |
|---|---|
| 产品是什么 | 银行柜面类桌面客户端（TellerKit），不是"套壳网页" |
| 框架 | **Tauri 2 + Rust 侧状态中心 + 你熟悉的前端框架**；GPUI 只借鉴思想，不全量替换 |
| 核心亮点 | 菜单包本地化（验签二进制）+ 全量树 + 权限快照本地剪枝 → 启动零菜单等待 |
| 安全红线 | 菜单隐藏只是体验层，**后端接口权限必须独立生效** |
| 产品化关键 | 业务包（`.bizpkg`）承载"机构新增业务"，主壳不动 |
| 最大瓶颈 | 不是写代码，是**真机外设联调 + 合规验收** |
| 第一步 | P0：骨架 + 菜单权限闭环（1–2 周，可运行、可演示） |

**诉求收敛结果：31 条诉求 → 18 条进 P0–P1，8 条后置到 P2–P3，5 条明确砍掉/延后。**

## 1. 对话脉络：6 轮是怎么长成今天这个形态的

| 轮次 | 你的问题 | 得到的结论 | 沉淀下来的诉求 |
|---|---|---|---|
| R1 | 桌面 App 是否比常开浏览器省资源？菜单树能否放本地文件、特殊后缀、按权限隐藏？ | Tauri 省资源成立；方案 = 二进制菜单包 + 签名 + 全量树 + 权限快照 | 启动速度、菜单本地化、防篡改、权限过滤（诉求 1–8） |
| R2 | 有这样做的嘛？ | 组合无公开先例，但每个构件都有生产实践（银行柜面 Electron 专利、Longbridge Pro/GPUI、libmenu-cache、Fyne RBAC） | 方案可成立，不需要改方向 |
| R3 | 完整形态产品还要做什么设计？ | 补齐安全纵深、交易引擎/离线、终端抽象、更新运维、效率、合规审计 | 诉求 9–20 |
| R4 | 能参考 Zed / GPUI 吗？ | 数据漂亮但 pre-1.0、生态绑死 Zed、迁移代价 97k 行；**Tauri 做骨架，GPUI 思想做肌肉** | 诉求 21（局部高性能表格） |
| R5 | 构思和开发就是我和 DeepSeek | 战略从"平台"降到"可运行 MVP"，定技术栈、P0–P3 路线、协作规程 | 诉求 22–25（开发方式约束） |
| R6 | 业务插件 / 业务包，机构新增业务 | 业务包 = 签名包（前端资源 + 元数据），不进包的是主壳地基；包供给能力、服务端授权 | 诉求 26–31 |

## 2. 诉求总表（全部 31 条）

优先级：**P0** 骨架必做 / **P1** 交易闭环 / **P2** 产品化 / **P3** 生产化 / **✂** 明确砍掉或无限延后

### A. 启动与资源（R1）

| # | 诉求 | 验收标准 | 优先级 |
|---|---|---|---|
| A1 | 桌面客户端替代常开浏览器，降低常驻资源占用 | 空闲常驻内存 ≤ 200MB；安装包 ≤ 30MB | P0 |
| A2 | 打开软件要快，菜单相关的启动延迟压到接近零 | 断网冷启动到首屏可点 ≤ 3s，其中菜单环节 ≤ 50ms | P0 |

### B. 菜单本地化与防篡改（R1）

| # | 诉求 | 验收标准 | 优先级 |
|---|---|---|---|
| B1 | 不同角色/岗位看到不同菜单树 | 3 个 mock 角色登录看到 3 套不同菜单 | P0 |
| B2 | 不要每次启动都请求服务端再解析菜单 | 启动阶段零菜单网络等待；网络只做后台版本探测（< 1KB） | P0 |
| B3 | 菜单树放在可同步的文件里 | `.mtree` 包可被服务端下发、可被客户端原子替换、可留 N-1 版本 | P0 |
| B4 | 特殊后缀，普通软件无法编辑 | 文本编辑器打开为乱码、无编辑器关联；篡改 1 字节即验签失败 | P0 |
| B5 | 完整性校验：私钥签名、客户端内置公钥验签 | 非对称签名（Ed25519）；MVP 允许 HMAC 过渡，但不宣传为"安全" | P0 |
| B6 | 验签失败要能降级 | 失败 → 拒绝该文件 → 回退服务端拉取 + 写告警日志 | P0 |
| B7 | 文件放应用数据目录，不用安装目录 | 落在 `$APPLOCALDATA`；Tauri fs scope 收窄到该目录 | P0 |
| B8 | 菜单包只存"全量结构"，不按角色打包 | 同一份 `.mtree` 服务所有角色；不做多包 | P0 |

### C. 权限（R1）

| # | 诉求 | 验收标准 | 优先级 |
|---|---|---|---|
| C1 | 不展示没有操作权限的菜单 | 无权限节点不可见；**父节点无权但有权的子孙必须保留**（关键用例） | P0 |
| C2 | 权限快照本地缓存，登录时下发 | 快照含 menuCodes / actionCodes / permVersion / shortcuts | P0 |
| C3 | 按钮级权限，不止菜单隐藏 | 页面内按钮按 actionCodes 过滤 | P1 |
| C4 | 权限变更同步：JWT 只带 userId + permVersion | 版本不一致才拉取；不为权限明细签发长 Token | P1 |
| C5 | 高敏感场景秒级生效 | 可叠加 WebSocket/SignalR 静默刷新快照，不重启 | P2 |
| C6 | 登出/切换账号/401 必须清快照 | 换账号后不残留上一账号菜单 | P0 |
| C7 | 安全边界必须写进文档和演示话术 | 明确"菜单隐藏 ≠ 安全"，后端接口独立鉴权 | P0 |

### D. 完整形态（R3）

| # | 诉求 | 验收标准 | 优先级 |
|---|---|---|---|
| D1 | 外设白名单（打印机/高拍仪/密码键盘/读卡器） | 非授权 USB/串口设备接入即阻断 | P2 |
| D2 | 离岗锁屏 + 动态水印（工号 + 网点号） | 超时/失焦/外设断开触发；锁屏后必须重新认证 | P3 |
| D3 | 剪贴板管控、敏感字段脱敏 | 交易中敏感字段禁止跨应用复制 | P2 |
| D4 | 交易 pending 落盘 + 恢复重放（untanking） | 断网提交不丢单、不重复记账 | P3 |
| D5 | 冲正状态机（Marked for Reversal / Roll Forward） | 不猜成败；提供"查账"+"发起冲正"两个入口；冲正需授权 | P3 |
| D6 | 离线降级有边界（`offline_capable`） | 资金类默认 false；只能服务端配置覆盖，包不能自称 | P1 |
| D7 | 终端抽象层（Printer / CardReader / PinPad / Scanner） | 换设备只改适配器，业务代码零改动 | P1 |
| D8 | 更新：原子替换 + 签名 + 失败回滚 + 灰度 + 保留 3 版 | 更新失败自动回退；交易中绝不弹窗要求重启 | P3 |
| D9 | 全键盘操作 + 快捷键可自定义 | 登录→选交易→录入→提交全程无鼠标 | P2 |
| D10 | 双屏：客户副屏确认，敏感信息不外推 | 客户屏只展示交易要素 | P3（先单屏） |
| D11 | 高频交易按客户画像置顶（动作预判） | 刷卡/输卡号后最可能交易置顶 | P3 |
| D12 | 三通道日志：tx_log / audit_log / diag_log | 核心日志留存 ≥3 年、重要 ≥1 年；不可篡改删除；异步上报 | P2 |

### E. 框架选型（R4）

| # | 诉求 | 验收标准 | 优先级 |
|---|---|---|---|
| E1 | 借鉴 Zed 的集中式状态（AppState + Entity 所有权） | Rust 侧持有用户/权限/菜单/外设/交易队列，前端只渲染+转发事件 | P0（思想落地） |
| E2 | 高性能表格等瓶颈模块局部评估 GPUI / GPUI Kit | 只在流水查询等模块做限时原型，不迁移主框架 | ✂（P3 之后） |
| E3 | GPUI / GPUI Kit 全量替换底座 | — | ✂ 砍掉 |

### F. 业务包插件化（R6）

| # | 诉求 | 验收标准 | 优先级 |
|---|---|---|---|
| F1 | 业务包机制，机构新增业务不动主壳 | 放一个包到目录 → 重启 → 菜单多出节点 → 页面可开 | P2 |
| F2 | 包内容：manifest / menus / permissions / routes / transactions / ui / templates | 缺任一必需项则拒绝加载并告警 | P2 |
| F3 | 不进包的东西：交易引擎、离线队列、审计、权限同步、外设驱动、更新器 | 包只能调主壳暴露的接口 | P2 |
| F4 | 包必须签名，验签通过才加载 | 未签名/签名错 → 不加载 + 告警 | P2 |
| F5 | 版本三元组 + 依赖 + 独立升级 + 保留 1–2 版回滚 | 包可单独下发升级，主壳不动；不兼容则跳过加载 | P2.5 |
| F6 | 菜单包与业务包解耦 | 菜单包只存基础框架菜单，业务菜单全由包注入 | P2 |
| F7 | 前端加载用 ES module + import map，通过 `window.__shellAPI` 白名单 | 不用 iframe 沙箱；CSP + 接口白名单兜底 | P2 |
| F8 | 业务包不做热插拔 | 安装/升级后"重启生效" | P2 |

### G. 开发方式约束（R5）

| # | 诉求 | 落地方式 | 优先级 |
|---|---|---|---|
| G1 | 单人 + AI，不要一次生成整个系统 | 任务粒度 = 一个文件 / 一个 trait / 一个页面 | P0 起 |
| G2 | 你定业务规则与验收标准，AI 出接口/实现/测试 | 每个任务先写清契约，再生成代码，你跑测试验收 | P0 起 |
| G3 | 每阶段必须"可运行" | 里程碑 = 能跑起来的闭环，不是"写完的模块" | P0 起 |
| G4 | 定位先做内部原型/技术验证 | 演示时必须说明"未做真机与合规验收" | P0 起 |

## 3. 已定的技术决策（ADR 速览）

| 决策 | 结论 | 理由 |
|---|---|---|
| ADR-01 桌面框架 | **Tauri 2** | 包小、常驻内存低、Rust 侧能管文件/外设/签名/更新 |
| ADR-02 UI 底座 | 你熟悉的前端框架（React/Vue/Svelte 择一） | 不为柜面场景换栈，学习成本才是单人项目最大成本 |
| ADR-03 状态架构 | Rust 侧集中式 `AppState`，前端纯渲染 | 借鉴 GPUI/Zed 的 Entity 所有权，避免前端状态分裂 |
| ADR-04 菜单存储 | `.mtree` 二进制包（MessagePack payload + Ed25519 签名） | 满足"特殊后缀不可编辑"+ 可验签 |
| ADR-05 菜单-权限分工 | 全量树在文件，权限快照在内存 | 一份文件服务所有角色；过滤毫秒级 |
| ADR-06 同步 | 版本号探测（`menuVersion` / `permVersion`） | 启动零等待，网络降级为后台 |
| ADR-07 本地存储 | SQLite（交易队列 / 日志 / 元数据）+ 应用数据目录下的包文件 | 单人可控，无需额外服务 |
| ADR-08 外设 | Rust trait + 适配器 + mock 先行 | 业务代码永久不碰硬件型号 |
| ADR-09 业务包 | 签名包 + 前端 ES module + 元数据，重启生效 | 单人可维护的"插件"最大公约数 |
| ADR-10 更新 | Tauri 官方 updater，全量 + 签名 + 回滚 | 增量留到生产化阶段 |

## 4. 目标架构

```
┌────────────────────────────────────────────────────────────┐
│ 前端 (WebView)   纯渲染 + 事件转发，不持业务真相            │
│   Shell UI  │  业务包 UI (ES module, __shellAPI)           │
└──────────────────────────┬─────────────────────────────────┘
                           │ invoke / event
┌──────────────────────────▼─────────────────────────────────┐
│ Rust 主壳：AppState（单一真相源）                            │
│                                                            │
│  MenuRepo     全量树 + 合并 + filter_visible                │
│  PermRepo     快照 HashSet + permVersion + 变更清空          │
│  PkgLoader    manifest 校验 → 依赖拓扑排序 → 菜单/路由合并    │
│  TxEngine     在线/离线判定 → 幂等键 → pending 队列          │
│  DeviceSvc    Printer/CardReader/PinPad/Scanner trait       │
│  AuditSvc     tx_log / audit_log / diag_log                 │
│  SecSvc       验签、外设白名单、剪贴板策略                    │
│  Updater      全量更新 + 回滚                               │
└──────────────────────────┬─────────────────────────────────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   服务端 API        本地 SQLite        .mtree / .bizpkg
   (菜单版本/权限/    (队列/日志/         (应用数据目录)
    交易/更新)        元数据)
```

**启动路径（P0 验收目标）**

```
读 .mtree (≤5ms) → 验签 (≤10ms) → 反序列化 (≤10ms)
  → 合并业务包菜单 (≤5ms) → 用权限快照递归剪枝 (≤1ms)
  → 渲染菜单 (首屏可见)
  ⟂ 并行：后台版本探测，不一致才静默下载新包
```

## 5. 核心数据契约（P0 动工前必须定稿）

### 5.1 MenuNode

```jsonc
{
  "code": "biz.deposit.withdraw",   // 唯一，与权限码体系对齐
  "parentCode": "biz.deposit",      // null = 根
  "title": "活期取款",
  "titleKey": "menu.deposit.withdraw",
  "type": "group | page | action",  // group 仅为容器
  "route": "/tx/withdraw",
  "icon": "cash",
  "sort": 10,
  "actions": ["action.withdraw.print", "action.withdraw.reversal"],
  "source": "shell | pkg:retail-v1", // 来源可追溯
  "status": "active | hidden"
}
```

### 5.2 权限快照（登录响应）

```jsonc
{
  "userId": "u_1001",
  "tellerNo": "T0231",
  "outletCode": "01023",
  "permVersion": 4821,
  "menuCodes": ["biz.deposit.withdraw", "..."],   // 只管叶子/可导航节点
  "actionCodes": ["action.withdraw.print", "..."], // 按钮级
  "shortcuts": { "biz.deposit.withdraw": "Ctrl+W" },
  "issuedAt": "2026-11-24T09:00:00+08:00"
}
```

### 5.3 过滤算法（唯一规则，必须有单测）

```rust
fn is_visible(node, menu_codes, action_codes) -> bool
// 规则：
//   1. node.code ∈ menuCodes → 可见
//   2. 或 ∃ 后代 d：is_visible(d) → 可见（父节点不连带隐藏有权的子孙）
//   3. group 自身不在集合但存在可见后代 → 保留（容器仍需存在）
//   4. action 节点只看 actionCodes
// 边界用例：父不在集合、子都在集合 → 父保留
//           父在集合、子都不在集合 → 子剪掉，父保留为空容器（或按配置隐藏）
```

### 5.4 `.mtree` 文件布局

```
[0..8)    magic  "MTKMTREE"
[8..10)   formatVersion u16 = 1
[10..14)  payloadLen  u32
[14..22)  menuVersion u64
[22..26)  shellCompatMin u16
[26..30)  shellCompatMax u16
[30..)    payload: MessagePack(全量菜单树)          // 无 JSON 明文
[末 64B]  Ed25519 签名 over sha256(header || payload)
```

落盘策略：写 `menu.<ver>.mtree.tmp` → `fsync` → `rename`（原子替换）→ 保留 N-1。

### 5.5 `.bizpkg` 结构

```
manifest.json     # id, version, minShell, maxShell, deps[], permissions[], entry, signature
menus.json        # 增量菜单：parentCode 挂接 + sort
permissions.json  # 本包声明的 actionCodes（必须与服务端对齐，不能自造）
routes.json       # path → ES module 入口
transactions.json # 交易码, idempotency, offlineCapable, devices[], authLevel
ui/               # ES module 前端资源
templates/        # 打印模板（套打）
```

### 5.6 日志三通道

| 表 | 内容 | 留存 |
|---|---|---|
| `tx_log` | 交易流水、幂等键、状态机迁移、重放记录 | ≥3 年 |
| `audit_log` | 登录/登出、菜单访问、授权、冲正、打印、外设调用 | ≥3 年（核心）/≥1 年（重要） |
| `diag_log` | 崩溃、性能、更新事件 | 滚动清理 |

## 6. 路线图

**估算假设**：单人 + AI，每天投入 2–4 小时；范围严格锁定，不许中途加需求。

### P0 · 骨架 + 菜单权限闭环（目标 1–2 周）

> 这是全项目的"演示核心"，先跑通，不碰外设、不碰交易。

## 7. 单人 + AI 协作规程（写给你自己看的纪律）

1. **一次只做一个文件 / 一个 trait / 一个页面**。超过 300 行的生成结果直接退回重拆。
2. **契约先行**：先写 Rust 结构体 + TS 类型 + 单测用例，再让 AI 填实现。
3. **测试是验收工具**：`cargo test` 红了就把失败用例贴回去，不要口头描述。
4. **每个里程碑必须能演示**：不能 `npm run dev` 起来的功能，一律不算完成。
5. **禁止 AI 自主扩范围**：任何"顺便优化一下"都记进 TODO，不当场做。
6. **上下文管理**：每轮对话只带相关 2–3 个文件，其余用摘要。
7. **决策留痕**：选型/取舍写进 `docs/adr/`，防止三个月后自己推翻自己。

## 8. 风险与红线

| 风险 | 影响 | 应对 |
|---|---|---|
| **Windows WebView2 内网部署** | 银行终端常无外网，Evergreen 装不上 | 必须准备 **Fixed Version 离线安装包**，安装器内嵌 |
| 银行终端锁 USB / 无管理员权限 / 域策略 | 装不上、外设驱动装不上 | P0 阶段就去目标机器验证一次（这是最贵的坑，越早越好） |
| 套打模板 / 密码键盘需厂商 SDK | P3 真机阶段可能推翻抽象层设计 | 抽象层先按"最坏情况"设计（返回结构体 + 错误码，不假设同步） |
| 合规（等保、日志留存、密码法） | 无法上生产 | 定位"内部原型/技术验证"，演示时明确声明 |
| 单人长期维护 | 业务包 + 主壳双版本矩阵失控 | 版本三元组 + 兼容性检查 + 只保 1–2 版 |
| `.mtree` 防篡改被误解为安全 | 审计/合规表述错误 | 文档与演示统一话术：**检测篡改，不防本机管理员** |
| AI 生成代码不可审查 | 技术债 | 每 PR 先写测试，Rust 侧强制 `clippy` |

**三条不可越过的红线**

1. 菜单/按钮隐藏 **永远** 不能替代后端鉴权。
2. 资金类交易 **永远** 不能由客户端或业务包单方面声明可离线。
3. 冲正 **永远** 不能由发起柜员单方面完成。

## 11.2 工作台的五层与八步

规格层 .specify/      ← 人写，AI 只读
契约层 contracts/     ← 唯一事实源，AI 只读

八步：1 写 spec（人）→ 2 评审（人）→ 3 分派 → 4 生成（AI）→ 5 门禁（工具）

**AI 只在 3–5 步。** 规格定义、批准、合并、发布都是人的职责。

## 11.5 178 包规模对当前的约束

现在只有 1 个应用、0 个业务包。但 R13 的结论里有四条**现在就要遵守**，否则 P2 会返工：

1. **常驻容器按池算，不按包算**——业务包数量增长时不许线性增加 iframe/Worker/WASM。
2. **清单聚合签名**——178 个包不允许逐个验签；启动只验一个 catalog。
3. **回滚单位是索引快照**，不是单个包。
4. **菜单可见 ≠ 包已加载**——两者必须显式分开。
