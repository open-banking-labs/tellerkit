# ADR-0003：`.mtree` 二进制包 + Ed25519 签名

- 状态：已接受
- 日期：2026-11-24

## 背景

需求原话是"菜单树放在一个可以同步的文件，特殊后缀，一般软件无法编辑"。
字面实现有两条路：加密（真不可读）与二进制 + 签名（不可改、可检测）。

## 决策

- 序列化：**MessagePack**（位置式，不写字段名）。
- 后缀：`.mtree`，文件命名 `menu.<version>.mtree`。
- 完整性：**Ed25519 签名**，覆盖 `sha256(头部 || payload)`，签名 64 字节附在文件末尾。
- 头部含 `format_version` / `payload_len` / `menu_version` / `shell_compat` 范围。

## 理由

1. 满足"一般软件无法编辑"：无编辑器关联、结构为二进制、手改即验签失败。
2. 非对称签名让私钥可以只存在于服务端构建环节，客户端只内置公钥。
3. MessagePack 比 JSON 小且解析快；位置式序列化不暴露字段名。
4. 头部显式带版本与长度，损坏/截断能被明确识别，而不是抛一个模糊的反序列化错误。

## 为什么不加密

菜单标题不属于机密（真机密是客户数据）。加密会引入密钥分发问题：
把对称密钥放进客户端，等于没有保护；用非对称加密又超出了 P0 的需求。
若将来确有保密需求，再在 payload 上加一层 AES-GCM，头部加 key id。

## 原子性

写入必须先写 `menu.<version>.mtree.tmp` → `fsync` → `rename`。
`.tmp` 永远不会被当成有效包读取；启动时顺带清理残留 `.tmp`。

## 安全边界

见 `docs/security-boundary.md`。**本文档不声称签名能防住本机管理员。**
