# 安全边界说明（必须与演示话术保持一致）

> 适用版本：P0
> 最后更新：2026-11-24
> 本文是 TellerKit 对外表述的**统一口径**。任何人解释"菜单权限"时，必须按本文说，
> 不允许出现"改了菜单就能越权""签名能防住本机管理员"这类表述。

---

## 1. 一句话结论

**菜单与按钮的可见性控制，是体验层，不是安全边界。**

真正的权限边界只有一条：**服务端对每一次请求独立鉴权**。
客户端做的一切（本地菜单包、权限快照、按钮过滤）只解决两件事：

1. 让柜员看不到用不了的功能，减少误操作；
2. 让启动更快，不把菜单渲染押在网络往返上。

---

## 2. 三层信任模型

```
业务包（签名）          服务端（授权）            客户端（渲染）
供给"能力"       ──▶   授予"权限"        ──▶    按快照剪枝
.bizpkg 声明             permVersion +             menuCodes /
权限码、页面、           角色-权限映射             actionCodes
交易元数据                                       → 可见性
```

三层的职责不能互换：

| 层 | 能做什么 | 绝对不能做什么 |
|---|---|---|
| 业务包 | 声明"我提供哪些权限码、页面、交易" | 自己造服务端不认识的权限码；声明资金类交易可离线 |
| 服务端 | 决定谁拥有什么权限；每次请求校验 | 信任客户端上报的权限 |
| 客户端 | 按快照隐藏入口；验签拒绝坏包 | 把"隐藏"当成"禁止"；决定交易成败 |

**一个业务包声明的权限码，如果服务端从未授予过任何人，那个菜单对所有人永远不可见。**
这本身就是一道防呆：包不能靠"我声明了"就获得能力。

---

## 3. `.mtree` 签名能做什么、不能做什么

### 能

- **检测篡改**：改一个字节（包括版本号）即验签失败，客户端拒绝该文件。
- **阻止非授权方下发菜单包**：没有服务端私钥就造不出能通过验签的包。
- **防止降级攻击的可检测性**：版本号在签名覆盖范围内，改小版本号同样会被发现。

### 不能

| 攻击 | 签名是否有效 | 说明 |
|---|---|---|
| 本机管理员替换整个文件 | 无效（验签失败） | 只能检测，不能阻止；他可以直接删掉文件 |
| 本机管理员改内存里的菜单树 | 无效 | 进程内数据不受签名保护 |
| 本机管理员改前端资源 | 无效 | 前端包不在签名链路内（P3 才考虑完整性校验） |
| 网络中间人替换包 | 无效 | 只能防"改"，不能防"阻断/重放旧包"——旧包需靠版本号单调递增 + 服务端记录来抵御 |
| 柜员直接调用后端接口 | **完全无关** | 这是服务端鉴权的职责，客户端拦不住 |

### 因此

- 可以对客户说："菜单包被改动会失效并自动回退。"
- **不可以**说："签名保证了菜单权限不可篡改。"

## 4. 必须向审计/客户交代的三个事实

1. **私钥只在服务端构建环节。** 客户端内置的只有公钥（P0 演示用的是公开的
   `DEMO_SEED`，生产必须替换，见 `crates/tellerkit-core/src/mock.rs`）。
2. **HMAC 过渡方案不等于安全。** 若因工期使用共享密钥 HMAC，只能表述为
   "完整性校验"，不能表述为"防篡改"。
3. **本地不存在不可篡改的文件。** 在用户自己的机器上，任何本地存储都可被
   拥有管理员权限的人替换；工程目标是"提高成本 + 可检测"，不是"杜绝"。

---

## 4.5 业务包模块：已进 sandbox iframe

业务包模块跑在 `sandbox="allow-scripts"` 的 iframe 里（`platform/sandbox.ts`）。
实测边界（Chromium 注入 hostile 包验证）：

| 能力 | 结果 |
|---|---|
| 父页面 DOM / `window.parent` | `SecurityError` |
| `localStorage` / `cookie` | `SecurityError` |
| `fetch` / XHR | CSP `connect-src 'none'` 拦截 |
| `__TAURI__` / `invoke` | 不存在，能力只能走白名单 |

白名单三项：`printVoucher`、`submitTransaction`、`log`，每项仍经 Rust 侧校验。

**仍然同进程**：iframe 与主壳共享渲染进程内存，侧信道未防。真正的进程隔离
（多 webview / 独立进程）是 P4。

准确说法："业务包由我们签名，运行在受限沙箱里，只能调用主壳开放的三个接口。"
不要说"业务包完全隔离"——同进程这一点必须承认。

## 5. 已知的 P0 简化（对上生产是硬阻断）

| 简化 | 风险 | 何时必须解决 |
|---|---|---|
| 公钥硬编码演示种子 | 任何人都能造包 | 接真实服务端前 |
| 权限快照仅内存 + 登录下发 | 重启需重新登录（可接受） | P1 接真实登录时 |
| 无权限变更推送（WebSocket） | 权限变更需重新登录才生效 | P2 |
| 业务包未实现 | 新增业务需改主壳 | P2 |
| 前端资源无完整性校验 | 改前端可绕过界面限制（但绕不过服务端） | P3 |
| 业务包模块无进程级沙箱 | 签名包内的代码可访问 DOM 与 window | P3 评估 Worker/iframe |
| 无外设白名单、无剪贴板管控 | 数据外泄通道敞开 | P2 |
| 日志未加密、未上报 | 不满足留存合规 | P2 |

### 已关闭的缺口（2026-11-25）

| 缺口 | 现状 |
|---|---|
| 传输明文 | ✅ `https://` 走 rustls + 内置根证书；`TK_REQUIRE_TLS=1` 拒绝明文端点 |
| 端点配置可被篡改 | ✅ Ed25519 分离签名（`endpoints.json.sig`），**先验签后解析**；配了公钥就必须签 |
| 演示开关被误用于生产 | ✅ 双重防护：正式构建后端拒绝（`dev_only()`），前端也不渲染面板 |
| 主机不幂等时离线挂起 | ✅ `TxHost::supports_idempotency()` 默认 false，未声明则拒绝 `offline_capable` |

### 仍未关闭

| 缺口 | 风险 | 何时必须解决 |
|---|---|---|
| 证书吊销（OCSP/CRL） | 私钥泄露后仍可冒用 | 接真实服务端前 |
| 企业自签 CA 支持 | 内网部署无法用内置根 | 按网点需求 |
| 配置签名私钥的保管 | 谁持有谁就能改端点 | 流程问题，非代码 |
| 账本仅字段级加密（`tx_queue.elements` AES-GCM） | 密钥与库同目录：能执行代码者可一并拿走；审计/交易日志仍明文 | P4 接 OS 钥匙串 |
| 业务包与主壳同进程（iframe 隔离，非进程隔离） | 共享渲染进程内存；侧信道未防 | P4 多 webview/独立进程 |
| 端侧后台重放 | ✅ 后台线程按 `TK_REPLAY_INTERVAL_SECS`（默认 60s）自动重放 | — |

## 6. 演示话术（照读版）

> "这个客户端把菜单树放在本地签名包里，启动时不请求服务端，所以打开很快。
> 每个用户登录时拿到一份权限快照，客户端在内存里把没权限的菜单剪掉。
>
> 需要强调的是：**这只是让柜员看不到不该看的功能**。真正的权限控制在后端，
> 每一次交易请求都会独立校验。就算有人把客户端的菜单改出来了，他也提交不了交易。
>
> 菜单包本身有签名，改一个字节就会失效并自动回退到服务端版本。但签名的作用是
> '检测篡改'，不是'防住本机管理员'——这一点我们不会夸大。"

## 7. 反模式清单（评审时必须打回）

- 把 `menuCodes` 当作接口鉴权依据。
- 在 JWT 里塞完整权限明细，并期望"改了 Token 也没用"。
- 让业务包声明 `offlineCapable: true` 就能离线做资金交易。
- 用"菜单没显示"来回应"为什么他能调这个接口"。
- 把 HMAC 校验宣传为"防篡改"。
