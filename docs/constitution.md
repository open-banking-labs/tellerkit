# 项目宪法（不可协商原则）

> 这份文件是**规则**，不是建议。任何人（包括 AI Agent）在仓库里做事，先读这里。
> 修订只能由项目负责人发起，走 `changes/` 提案流程。
> 每条都标注了「靠什么检查」——没有检查的条文等于没有条文。

---

## 第 1 条 · 契约唯一事实源

`contracts/` 是接口、字段、错误码的唯一事实源。**AI 不得修改契约来迎合实现。**

- 实现与契约不一致 → 改实现。
- 契约缺失或自相矛盾 → 在 `changes/` 写提案，由人批准后再改契约。
- 检查：`tools/check-contracts.mjs`（字段/命令与代码双向比对）

**为什么**：让 AI 改契约是最省事的"通关方式"，也是把系统改烂最快的方式。
契约一旦变成"实现写完再补的文档"，权限边界和版本兼容就全部失效。

---

## 第 2 条 · 抽象分离

抽象层不得 import 实现层；跨层 import 一律禁止。

- `crates/tellerkit-core` 不得依赖 `tauri`、不得依赖 `src-tauri`。
- `src/`（前端）不得 import 核心库，不得自己判断权限。
- 业务包只能调主壳暴露的接口，不得直接访问文件系统/网络。

检查：`tools/check-boundaries.mjs`

---

## 第 3 条 · 权限边界

**菜单与按钮的可见性只是体验层，不是安全边界。** 真正的权限控制必须在服务端接口独立生效。

- 客户端不得把"菜单没显示"当作"该操作不被允许"的理由。
- 端侧 AI（将来）：AI 建议不等于授权，AI 预填不等于提交。
- 检查：`tools/check-ai-rules.mjs`（security-boundary.md 关键表述存在性）

---

## 第 4 条 · AI 的职责边界

工作流是 8 步：规格 → 评审 → 分派 → 生成 → 门禁 → 人工评审 → 合并 → 索引快照。

**AI 只在第 3–5 步工作。第 1–2 步（定义规格）和第 6–8 步（批准、合并、发布）是人的职责。**

- AI 可以起草 spec 和 tasks 的**初稿**，但不能自行新增 spec 场景、不能修改验收标准。
- AI 不能批准发布、不能碰授权决策、不能代表人工评审。

检查：靠流程约束（`tasks.md` 每项必须引用 spec 场景 ID，人工评审时核对）

---

## 第 5 条 · 门禁即裁决

门禁结论必须由**工具执行的 exit code** 取得，**不接受 AI 自报"已通过"**。

- 门禁失败不自动重试。一次失败 → 一次分析 → 一次人工决策。
- 门禁报告必须给出可操作的修复建议，不能只报红。
- 检查：`npm run gate` 是唯一入口，CI 与本地同一条命令。

**为什么**：自动重试会让 AI 反复试错、掩盖真实问题、烧掉预算，最后得到"改到测试通过"而不是"改到正确"。

---

## 第 6 条 · 上下文与改动纪律

- 一次任务 = 一个文件 / 一个 trait / 一个页面。超过 300 行新增的产出直接退回重拆。
- 读取顺序固定：最近的 `AGENTS.md` → 相关 `contracts/` 条目 → 对应 `spec.md` → `plan.md` → `tasks.md`。
- 不逐层扫描整个仓库，按任务类型直接定位。
- 禁止 AI 自主扩范围：新需求写进 TODO，不当场做。

---

## 第 7 条 · 减法优先

不过度设计。新能力按"痛点出现"启用，不按"将来可能需要"启用。

- 全量菜单树 + 权限快照（不做按角色分包）
- 业务包 = 前端资源 + 元数据 + 签名（不做 Rust dylib 动态加载）
- ES module 加载（不做 iframe 沙箱，直到出现不可信第三方包）

---

## 第 8 条 · 决策留痕

任何选型、取舍、被否决的方案，写进 `docs/adr/`。契约变更写进 `changes/`。
三个月后推翻自己时，必须有据可查。

---

## 第 9 条 · 业务包是不可信代码

主壳必须假设业务包会崩溃、会卡死、会尝试越权。

- 容器池化：iframe / Worker / WASM 实例按需创建、LRU 回收，**不按包数量常驻**。
- 配额与熔断：拒绝默认、配额驱动、失败即熔断。
- 检查：P2 引入 `tools/check-bizpkg.mjs` 做静态冲突检查（菜单挂接点/路由/权限码/快捷键/设备能力）

---

## 第 10 条 · 端侧 AI 只预留，不实现

- 预留的是**契约位置和数据结构**，不是功能：`assist.*` 命名空间、`aiAssistCapable` 字段、`ai_suggestion` 审计事件类型、AppShell 的 assistant 插槽。
- 不写代码、不接模型、不做 UI、不采集数据、不做权限判断。
- 将来接入时不需要改契约、不需要改权限模型、不需要改审计模型。

**这条现在写死，将来不需要重新讨论。**

---

## 第 11 条 · 深模块 / 窄接口

模块化不是按文件或技术层切分，而是按信息隐藏切分：内部状态私有，对外只暴露少数接口，
接口面必须显著窄于实现面。判定以 deslop-please 的四类反模式为准：module-cycle、tangle、
field-leak、shallow-module。

- 跨模块不得直接读写对方结构体字段；DTO 同样字段私有，用构造函数/访问器，跨语言序列化
  形状由契约门禁（ts-rs + fields.json）保证，不因私有化而改变。
- 每个 crate 只 `pub` 能力域门面；内部模块用 `pub(crate)`，`lib.rs` 不得平铺导出全部内部实现。
- 单个对象对外 `pub fn` 超过 12 个必须评审：拆成多个深模块，或把调用方的组合逻辑收进模块。
- 修复必须从第一性原理整体修；禁止 `--update-allow` 批量静音，豁免需逐条人工批准并登记理由。
- 检查：`tools/check-module-depth.mjs`（本机 `npm run gate` 第 7 道）+ 构建机 `deslop-please`。

---

## 附：违反宪法时会发生什么

| 违反 | 后果 |
|---|---|
| 改了 `contracts/` | 门禁红 + 提案未批准前不得合并 |
| 前端自己判断权限 | `check-boundaries` 红，直接拒绝 |
| AI 自称"测试已通过" | 视为无效；以 `npm run gate` 的 exit code 为准 |
| 一次提交过快照落盘 | 代码评审直接打回（ADR-0005） |
| 跨模块直接读写字段 / 内部模块全 `pub` | `check-module-depth` 红，评审打回 |
| 为将来可能的需求先写代码 | 评审打回，记入 `docs/adr/` 的"被否决方案" |
