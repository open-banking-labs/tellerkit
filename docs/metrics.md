# 指标

> 数据源：`.agents/dispatches/*.json`（W4 的派发记录）
> 生成：`npm run metrics`（或 `node tools/metrics.mjs --json`）

## 为什么要有这一层

W3 解决了"谁说了算"，W4 解决了"派活留痕"。但 50 条记录躺在目录里，
没人会去翻。可观测的作用是在指标变差时**指出下一步去改什么**。

所以本文件里每个指标都有「变了该做什么」。如果一个数字变了却不知道该干嘛，
它就不该出现在报告里。

## 指标

| 指标 | 定义 | 变了该做什么 |
|---|---|---|
| `total` / `decided` / `undecided` | 记录数 / 已裁决 / 未裁决 | `undecided > 0`：任务被遗弃或裁决被跳过。**未裁决等于没有结论**，先补裁决再谈别的 |
| `reject_rate_pct` | `(FAIL + OUT_OF_SCOPE) / decided` | > 30%：先看验收命令是否可执行（命令本身坏了会伪装成 FAIL）；再看任务是否拆得太粗（>1 文件 / >1 trait） |
| `out_of_scope_rate_pct` | `OUT_OF_SCOPE / decided` | > 10%：提示词里的白名单说明不够硬，或任务天然需要跨文件却只给了一个路径。**不要**通过放宽白名单解决 |
| `duration_ms.median` | 已裁决任务的验收耗时中位数 | > 10 分钟：验收命令可能包含全量构建，拆出针对性命令（只跑相关模块） |
| `duration_ms.p90` / `max` | 尾部耗时 | 与中位数差一个数量级：说明有个别任务在跑全量，定位到 `by_task` 里那个任务 |
| `by_preset` | 按角色分组的打回率 | 某个 preset 持续高：该预设的指令需要收紧，而不是怪任务 |
| `by_layer` | 按层次分组的打回率 | `docs` 层高：文档任务的验收命令太弱（`npm run gate` 验不到文档内容） |
| `by_task` | 按任务分组的打回率 | 某任务反复打回：任务本身有问题，拆掉或重写，不要重试 |
| `trace_issues` | 记录引用的任务已不存在 | 任务被删/改名后，旧记录成了无主证据。补回任务或归档记录，否则历史无法解释 |

`—` 表示没有数据，不等同于 0。样本 < 5 条时报告会明确说"别对比例下结论"。

## 怎么读

```
npm run metrics
```

```
派发记录 · 6 条（已裁决 5 / 未裁决 1）
  打回率      40%
  越界率      20%
判断
  · 1 条派发没有裁决：未裁决等于没有结论。
  · 打回率 40% 偏高：先看验收命令是否可执行、再看任务是否拆得太粗。
  · 越界率 20% 偏高：提示词里的白名单说明可能不够硬。
  · 记录 T-99 的追溯已失效：任务已不在 tasks.md（被删或改名）。
```

## 已知缺口

| 缺口 | 影响 | 何时补 |
|---|---|---|
| 没有 token / 成本指标 | 无法回答"这轮花了多少钱" | 宿主（DSH）上报用量后写入记录 |
| 没有重跑次数 | 无法区分"一次做对"与"试了五次" | 记录增加 `attempt` 字段，由派发器递增 |
| 没有时间维度趋势 | 只能看当前快照，看不到"在变好吗" | 记录数 > 50 后再考虑按周聚合 |
| 指标不进门禁 | 指标用于决策，用于拦截会逼人刷指标 | 保持现状 |

## 反模式

- 把打回率当成 KPI：会让 Agent 学会"挑软任务"或"改验收命令"。
- 用越界率惩罚 Agent：越界多半是任务定义问题，不是执行问题。
- 在样本 < 5 时下结论：这是最贵的误判，因为早期改动往往决定后面所有习惯。
