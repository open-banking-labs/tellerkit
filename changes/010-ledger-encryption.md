# 010 账本字段加密

## 现状

`tx_queue.elements` 是**明文 JSON**，里面是账号、户名、摘要。
任何人拿到 `tx.db` 就能读到这些数据——技术支持拷走、备份系统导出、
期末审计存档，都是现实路径。

`tx_log` 与 `audit_log` 不含完整账号（前者只有金额与流水号，后者是操作描述），
所以本轮只处理 `tx_queue`。

## 建议

用 AES-256-GCM 加密 `elements` 列，格式 `v1:<hex nonce>:<hex ciphertext>`：

- 密钥 32 字节，首次启动生成在应用数据目录 `ledger.key`（Unix 下 0600）；
- 每次加密用新随机 nonce（同内容两次加密结果不同）；
- 读取时没有 `v1:` 前缀按明文处理——**升级不炸老账本**。

## 能防什么

| 场景 | 效果 |
|---|---|
| 只拷走 `tx.db` | 读不到账号 |
| 拿到旧备份但没有 `ledger.key` | 历史交易仍是密文 |
| 数据库被改动 | GCM 校验失败，直接报错而不是解出垃圾 |

## 不能防什么（必须如实说）

**密钥文件就在旁边。能执行代码的本地攻击者可以两样一起拿走。**

这不是"账本安全了"，是"提高单文件泄露的成本"。真正的保护要等 OS 钥匙串：
Windows DPAPI / macOS Keychain / Linux Secret Service。那是 P4 的活。

## 影响

- `packages/journal-sqlite/src/cipher.rs`（新增）
- `SqliteJournal::open` 会创建 `ledger.key`
- 老库无需迁移：无前缀即明文，读取时兼容
- 新增依赖 `ring`（已在依赖树中，经 rustls）

## 风险

1. **密钥丢失 = 队列无法恢复**：挂起交易解不出来。密钥必须与应用数据一起备份，
   但**不能**与数据库放在同一个备份介质上（否则加密失去意义）——运维需知道这条。
2. 解密失败一律报错（不吞异常），所以密钥损坏会表现为"待重放队列不可读"，
   而不是静默丢单。
